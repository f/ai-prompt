Vibecoding works best when you separate thinking from doing. This walkthrough shows a realistic way to use AI Prompt blocks inside a production tutorial: we are going to design, implement, review, and reject changes while building a small Gutenberg block.

The example is intentionally not another AI-related block. The target is a plain Tip Card block: the kind of reusable callout authors use in documentation, course material, changelogs, and developer guides. That keeps the tutorial grounded in familiar WordPress work while still showing why prompt-specific presentation is useful.

A prompt is part of the technical artifact. If readers only see the resulting code, they miss the decisions that shaped it.

Using prompts as visible tutorial material: brainstorming, planning, coding, rejecting, and reviewing.

What we are avoiding

A complicated app. The target stays small so the Gutenberg concepts remain visible.

A normal code block can show source code, but it cannot show the surrounding workflow: which model was used, whether the prompt was exploratory or implementation-oriented, what files were in context, which tools were available, and which generated patch should be accepted or rejected. The AI Prompt block fills that gap.

The target: a simple Tip Card block

Before asking an agent to edit files, define the destination in boring product terms. The Tip Card block should let an author insert a short callout with a title, body text, and visual tone. The tone might be Info, Success, Warning, or Danger.

This is a good learning block because it touches the core Gutenberg surfaces without adding unrelated complexity. You get block.json, static serialization, sourced attributes, RichText, InspectorControls, styles, and block supports. You do not need remote APIs, custom database tables, dynamic rendering, or authentication.

Why a Tip Card?

It is simple enough to understand in one post, but still realistic enough to teach block attributes, editor controls, saved markup, and validation risk.

  • The reader should understand what the block does before seeing any code.
  • The implementation should be small enough to review in one sitting.
  • The final markup should be stable, readable, and safe to store in post_content.
  • The tutorial should show judgment, including a rejected patch, not just a happy path.

Step 1: brainstorm the block without writing code

The first prompt is deliberately not a coding prompt. At this stage, the job is to clarify the author experience. What problem does the block solve? Which controls belong in the sidebar? Which features should be postponed? This avoids the common vibecoding failure mode where the agent starts editing before the scope is clear.

Notice that the context is conceptual rather than file-based. We point the model at the Block Editor package, block.json, and the writing situation. That is enough for a useful product/design pass.

Step 2: plan the plugin files

Once the shape of the block is clear, ask for a file-level plan. This is where the AI Prompt block starts doing more than a code fence could: the file tree shows readers the expected project layout before any patch is accepted.

The goal of this step is not to write perfect code. The goal is to make the agent explain the boundaries: what belongs in block.json, what belongs in edit.js, what belongs in save.js, and what belongs in shared CSS. If the file plan is confused, the implementation will usually be confused too.

Checkpoint before coding

If the file tree or block responsibilities are still vague, stop here. Ask for a better plan before letting an agent touch files.

Step 3: generate the first implementation patch

Now we can ask for an implementation. This prompt is specific: define the attributes, use RichText in the editor, use a SelectControl for the tone, and serialize a static <aside> in save.js. The prompt also states what not to do: keep supports.html disabled and rely on block supports for alignment.

The diff shown here focuses on block.json because the block contract is the part worth teaching first. Attributes are the bridge between the editor and the saved content, and sourced attributes are one of the Gutenberg concepts that often surprises engineers coming from React-only apps.

Step 4: reject the clever-but-bad patch

A realistic vibecoding workflow includes bad ideas. Sometimes the model suggests something that looks useful but violates the platform. In this case, it tries to put React state and click handlers directly into save.js so the saved block becomes collapsible.

That is wrong for a static block. The save function is not a mounted React component; it is a serialization step. The returned JSX becomes HTML in post_content. Hooks like useState do not belong there, and event handlers in saved markup are not the right frontend architecture for Gutenberg blocks.

Rejecting this patch is part of the lesson. If the product really needs collapsible behavior, you have better choices: use native HTML like <details>, add a focused viewScript, or make the block dynamic if server rendering is part of the requirement. Do not paper over the Gutenberg lifecycle just because the agent produced plausible React.

Step 5: verify it like a release

After implementation, use the model for review rather than more generation. This prompt asks for release-minded checks: block validation, accessibility, selector consistency, frontend rendering, build output, and plugin packaging. That is the difference between “the agent produced code” and “the block is safe to ship.”

A useful review should include both editor and frontend checks. Insert the block in a post, save it, reopen the editor, confirm there are no validation warnings, then view the post on the frontend and inspect the generated markup. Finally, build the plugin zip and confirm it contains only the files a user needs.

What this example is trying to teach

The important part is not that a Tip Card block is difficult. It is that the workflow is visible. Readers can see the difference between brainstorming, planning, coding, rejecting, and reviewing. That distinction gets lost when every prompt is flattened into a code block.

  • Use broad prompts for product thinking before asking an agent to edit files.
  • Use planning prompts to identify the file tree and implementation boundaries.
  • Use code prompts only after the target files and acceptance criteria are clear.
  • Show rejected patches so readers learn the engineering judgment, not just the success case.
  • Use final review prompts to teach production discipline: validation, accessibility, packaging, and docs.

In a real tutorial, you could follow this with the actual Tip Card source code. The AI Prompt blocks would remain useful because they preserve the reasoning around the code: why the block exists, which files mattered, and which generated changes were accepted or rejected.
